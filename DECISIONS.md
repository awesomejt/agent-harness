# DECISIONS.md

Living record of important design decisions for agent-harness.

Entries record design intent, not implementation completion. Earlier entries remain historical; D009 revises D007 scope, D010 clarifies D004 execution paths, and D015–D016 align the implementation blueprint and ownership boundaries with Rust. New decisions identify superseded scope and the phase that must supply validation.

## 2026-11-01 — D001: Name

- **Decision**: Repository and project name is `agent-harness`. CLI command is `ah` (or `agent-harness`).
- **Rationale**: Explicit about the role; easy to search; leaves room for modes, agent sync, fallback, and Ralph loops.

## 2026-11-01 — D002: LiteLLM scope

- **Decision**: LiteLLM is used only for local models, open-weight subscriptions, and OpenRouter. It is **not** used as a proxy for cloud subscription traffic that would violate provider ToS.
- **Rationale**: Avoid account suspension or request refusal. Native CLIs are driven directly for those providers.

## 2026-11-01 — D003: Operational modes

- **Decision**: Support three modes via CLI flag (MVP) and later via per-prompt front-matter:
  - `local-only` — LiteLLM only.
  - `cloud-only` — native CLIs only.
  - `local-first` — LiteLLM first, native CLI fallback on failure.
- **Rationale**: Explicit control at the entry point; matches user preference for CLI first, front-matter later.

## 2026-11-01 — D004: Dual-path executor and three capacities

- **Decision**: Two backends — `LiteLLMExecutor` and `NativeCLIExecutor`. Support primary agent, specialized agent, and fallback (fallback only in local-first).
- **Rationale**: Clean separation of ToS-safe routing from direct CLI use; covers the three requested capacities.

## 2026-11-01 — D005: LiteLLM ownership and OpenCode sync

- **Decision**: Harness owns LiteLLM endpoint, model groups, and routing policy. When driving OpenCode in a local-capable mode, sync the provider block into the **project-level** OpenCode config (overrides global OpenCode settings for that project only). Global OpenCode config is left alone. `--no-sync` available.
- **Rationale**: Single source of truth; avoids maintaining two routing configs; keeps other tools/manual sessions unaffected.

## 2026-11-01 — D006: Canonical agent format

- **Decision**: Markdown + YAML frontmatter is the canonical format. Sync maps by name into each provider’s expected location (OpenCode, Claude, Gemini, Grok, Codex TOML, Pi Skills, etc.).
- **Rationale**: Matches the de facto standard already used by OpenCode, Claude Code, Gemini CLI, and Grok Build.

## 2026-11-01 — D007: Original MVP scope (superseded below)

- **Decision**: Start with OpenCode for local models + OpenRouter (via LiteLLM) and direct OpenCode runs. CLI `--mode` flag first. Agent sync for OpenCode. Single / sequence / Ralph modes. Pi and other native CLIs later. Other open-source subscription fallbacks stay inside LiteLLM.
- **Rationale**: Smallest useful surface that exercises the dual-path design and the user’s existing LiteLLM instance.

## 2026-11-01 — D008: Rust and binary installation direction

- **Status**: Accepted implementation direction for planning; concrete dependencies remain open.
- **Decision**: Use Rust for the CLI and target prebuilt platform binaries as the primary installation experience. Keep `agent-harness` as the project/repository name and `ah` as the command. Choose a distinct Cargo package name in Phase 1 because the public package name is occupied.
- **Rationale**: The user prioritizes easy installation, prefers compiled distribution, and is willing to learn Rust with AI assistance. Python runtime management and direct ai-queue code reuse are secondary concerns.
- **Validation**: Phase 1 proves the OpenCode integration; Phase 2 produces the first installable binary. Initial and expanded platform support are declared only with build/run evidence.

## 2026-11-01 — D009: First slice before core MVP

- **Decision**: Phase 2 delivers one real project coding run through OpenCode + LiteLLM in local-only mode. Phase 4 closes the core MVP with all operational modes, configured fallback, and named OpenCode agents. Sequences and Ralph are separate later milestones, followed by additional runtimes and optional resource awareness.
- **Supersedes**: D007, the original requirement to include single/sequence/Ralph in the first MVP; no full-product workflow goal is dropped.
- **Rationale**: Start learning through useful execution quickly. Do not wait for every workflow or provider.
- **Validation**: Each usable phase records representative tasks and direct-tool comparisons in PROJECT.md. Goals and exit evidence are in docs/SPECIFICATION.md and docs/IMPLEMENTATION.md.

## 2026-11-01 — D010: Separate model route from runtime transport

- **Decision**: Preserve LiteLLM and native routes as policy boundaries. OpenCode supplies the coding-agent loop on either route; ACP or another supported interface is its transport. `LiteLLMExecutor` / `NativeCLIExecutor` are conceptual paths, not mandatory concrete type names. Raw HTTP completions alone do not satisfy a coding milestone.
- **Clarifies**: The earlier architecture sketch that equated the LiteLLM path with a raw chat request and native execution with any subprocess.
- **Rationale**: The same OpenCode process can use LiteLLM or a native model target. Mode policy must control effective model routing, including inherited settings and subagent choices.
- **Validation**: Phase 1 tests transport/model control; Phases 2–3 test routing isolation. No custom inner tool loop is planned for MVP.

## 2026-11-01 — D020: Fail-closed experiment permissions

- **Decision**: Before P1.2 live work, use a headless default-deny policy for all tool actions. Allow only an explicit trusted grant bound to one complete attempt-specific request and an advertised allow-once option. Consume grants on the next request; never persist them or select allow-always. Prompting is unsupported in the experiment and policies requiring it must fail before launch, regardless of TTY availability.
- **Responses**: Select an advertised denial for ungranted actions; otherwise cancel, or stop if the transport cannot represent cancellation. Malformed identities/options fail the attempt. Response delivery failure triggers cleanup and possible uncertainty, never approval or a more permissive retry.
- **Rationale / alternatives**: Blanket project-write or shell grants would widen permission beyond a reviewed action. A TUI/approval timeout is unnecessary for the narrow experiment; default denial is deterministic and works headlessly. Interactive UX and broader declarative policies remain consuming-phase choices, not implicit runtime defaults.
- **Boundary**: [Execution contract](docs/EXECUTION.md#permissions-and-headless-operation) specifies the adapter preflight gate. `src/permission.rs` is a transport-independent experiment with synthetic normalized request tests, not an ACP wire schema or live security claim. No new dependencies, commands, model calls or backend launches. P1.2 must verify actual transport mapping and enforcement before live work; P1.3 proves denied-action and lifecycle behavior. Earlier routing/transport decisions remain unchanged.
- **Evidence**: [P1.6 policy fixtures](docs/evidence/p1-6-permission-policy.md). This resolves the pre-live permission decision only; Phase 1 remains open.

## 2026-11-02 — D025: Project routing ownership and fail-closed transactions

- **Decision**: P2.3 manages four routing values in project `opencode.json`: `provider.ah-litellm`, `enabled_providers`, `model`, `small_model`. The sole enabled provider is `ah-litellm`, using the selected existing alias for primary/helper models and `{env:NAME}` for its key. A private project `.ah-opencode-owner.json` receipt records the last generated values; `.ah-opencode.lock` serializes cooperating harness writers. No HOME/global configuration is read or written. Inactive sibling provider definitions remain byte-for-byte preserved; the enabled-provider allowlist is exact.
- **Preservation/conflicts**: Strict bounded JSON only, rejecting duplicate keys at every depth, JSONC, symlinks and nonregular transaction files. Preserve every unmanaged byte, including whitespace, by replacing only borrowed JSON value spans and inserting absent managed fields. Existing unowned routing fields refuse adoption, even if equal; exact matching `--no-sync` configuration needs no receipt. Later manual changes to owned values refuse updates. Receipt schema is the exact four-field generated-value object; it is an ownership aid, not authentication against a hostile project author.
- **Transaction**: Read-only planning precedes writes. Apply takes a nonblocking Unix advisory lock, compares exact config/receipt snapshots, stages same-directory files (0600 for new files; existing config mode preserved) with exclusive creation, flushes, renames config then receipt, and syncs the project directory. Failure/crash between replacements leaves an ownership mismatch that refuses subsequent sync; no automatic rollback or replay. Operators must inspect the config/receipt and reconcile their intended settings manually. Stale temporary files are inert and never interpreted as ownership. The stable lock file is retained to avoid replacing lock inodes.
- **Limits**: The two files are not a single atomic durable transaction. Advisory locking protects cooperating harness processes; an external editor that ignores the lock can race the final snapshot check/rename. Avoid concurrent external edits. After `session/new`, the ACP `mode` option must be exactly NAME before any prompt.

A non-default effort exits 2 before runtime discovery, reachability checks or project writes on every route; preview reports the refusal.
- **Fallback**: the local-first fallback carries the same agent; the recovery guard now also requires the same agent name and identical effective rules on both attempts. The native fallback's model follows D037.

## 2026-11-03 — D039: Opt-in version-1 machine records with unchanged exits

- **Selection**: `ah single ... --output human|jsonl`; `human` is the default and is unchanged byte-for-byte. The exact adjacent pair `--output jsonl` selects machine mode before full validation, so a rejected machine invocation (including a duplicate option or missing prompt) still ends in a result record. Any other value rejects with exit 2 in human mode. `--output jsonl --preview` rejects with exit 2; preview stays human-only.
- **Stream**: stdout carries only UTF-8 JSON Lines, one object per `\n`-terminated line. The final assistant response moves from raw stdout into the terminal record's `response`. Human diagnostics stay on stderr in their existing, unversioned format. The envelope is `v` (1), `seq` (0-based, strictly increasing in stdout order), `run`, `type`, `ts_ms` (wall clock), `elapsed_ms` (monotonic) and `attempt` on attempt-scoped records. Record types: `run.started`, `attempt.started`, `attempt.session`, `attempt.prompt_submitted`, `attempt.usage`, `attempt.activity`, `attempt.backend_stop`, `attempt.cleanup`, `fallback`, `result`. The [execution contract](docs/EXECUTION.md#p47-machine-output-d039) defines fields.
- **Terminal record**: exactly one `result`, always last: `outcome` (`succeeded`/`failed`/`rejected`/`cancelled`/`uncertain`, an explicit mapping of exits 0–4, never Rust enum serialization), `exit`, `reason` (static harness text, not a stable code), `response`, per-attempt summaries, `fallback`, `recovery`, `diagnostics_omitted` and `records_dropped`. Unknown metrics are `null`, never zero; `turn_tokens` is always `null` with the tested runtime.
- **Delivery**: one ordered writer thread with a 256-record queue. Non-terminal records are best-effort: a full queue drops them, leaving a counted `seq` gap; activity counters are cumulative and repeated in the result, so totals are never lost. The result is written after every queued record within a two-second budget after the final outcome. If it is not delivered, exit 0 becomes 1 (output failure, as in human mode); other exits are unchanged. A missing or unterminated result means the consumer must rely on the exit code and treat effects as unknown.
- **Redaction**: no prompt, partial assistant text, reasoning, tool arguments, raw stderr, provider errors, paths, endpoints, environment names or key values. The backend session ID uses the existing 128-character, non-ASCII-escaped form. `response` is untrusted backend text.
- **Compatibility**: consumers refuse any `v` other than 1. Within v1, new record types, new optional fields and new `backend_stop`/`route` values may appear and must be ignored or treated as unknown; removal, renaming, retyping, meaning changes or a new `outcome` value require v2.
- **R03-REC1 (declined)**: a post-submission failure without a trustworthy terminal response remains exit 4, even with zero grants and zero completed tool calls. Absent tool events do not prove no tool ran (D031), and the adapter still cannot classify provider rejections. The result instead exposes `prompt_submitted`, `backend_stop: null`, `grants` and `tool_events`, so a consumer can apply its own policy. No fallback or replay follows from either reading.
- **Headless**: unchanged: stdin is read only for `--prompt-file -`, permission requests are answered by the noninteractive policy, and no TTY prompt exists. Machine mode adds no wait on stdin or stdout beyond the bounded delivery budget.
- **Evidence/boundary**: [P4.7 evidence](docs/evidence/p4-7-machine-output.md). The machine contract covers `single` only; sequence records and durable workflow state are implemented in Phase 5 (D044).

## 2026-11-03 — D043: Trusted verification gates for single runs, scheduled before sequence decisions

- **Context**: P4.6 R1 recorded a coder `succeeded`/exit 0 with no edit; only an independent check caught it. The [Phase 4 review](docs/reviews/phase-04.md) scheduled P5.5 first in Phase 5 as the remedy. The P5.5 card had depended on P5.1, but gate semantics need no sequence ordering, context or state choice. Sequences, Ralph and single runs all consume the same gate.
- **Order**: P5.5 now depends on P4.9, P5.1 on P5.5, and P5.2 on both. The phase contents and P5.6 gate are unchanged.
- **Source and authorization**: only the harness config may define checks, as `checks.NAME = {argv, timeout_secs?}`. NAME uses the agent-name grammar. `argv` is a 1–64 element vector (at most 4096 bytes each, no NUL), never a shell string. Its program is an absolute path or a bare name. A relative path such as `./scripts/check.sh` rejects, because it would resolve inside the agent-editable project. `timeout_secs` is 1–86400 seconds, default 600; config holds 1–64 checks. Declaring a check never runs it: only `ah single ... --verify NAME` authorizes one check per run, mirroring D024's `--permissions trusted`. Prompts, agent definitions, model output and (in later phases) sequence prompt metadata cannot define a command; whether metadata may reference a name is decided in P5.1.
- **Pinning**: the check is resolved with the request, before key lookup, stdin, runtime discovery, network checks or writes. A bare name is found on absolute PATH entries only. The program is executed by its found absolute path, not canonicalized, so multi-call proxies such as rustup keep working. The found entry and every symlink hop to the final program must lie outside the canonical project; otherwise exit 2 (untrusted). Agent edits to `ah.json`, PATH or the project during the turn cannot change which program runs. This guards against project-content substitution only. A trusted agent has host privileges and can alter files outside the project; a check executes current project content (tests, build scripts) by design. A pass verifies the project's check as it stands after the run, not the diff's intent.
- **Execution**: after the final backend outcome (whichever local-first attempt produced it) and confirmed runtime cleanup, only if that outcome is success. argv runs without a shell, in the canonical project directory, in its own process group. stdin is closed; stdout and stderr both go to the harness stderr, so stdout stays the response or machine records. The environment is inherited minus every configured `api_key_env` name and `AH_RUNTIME_API_KEY`/`OPENCODE_API_KEY`. The bound is the check's own timeout, separate from `--timeout-secs`. Timeout or cancellation sends SIGTERM to the group, then SIGKILL after two seconds. Every exit, including a pass, terminates lingering group members and confirms group absence with the existing bounded process-group check.
- **Outcomes**: verification `status` is `not_run`, `passed`, `failed` (nonzero exit or signal), `timed_out`, `cancelled` or `error` (spawn/wait failure), with `agent_outcome` recorded separately. Exits: no `--verify` keeps D024 unchanged; backend non-success keeps its exit and `not_run`; passed 0; failed/timed_out/error 1; cancelled 3; unconfirmed check cleanup 4 (takes precedence). A run without `--verify` is never labeled verified. Machine output (v1, additive per D039) adds `verification.started`/`verification.finished` records and a result `verification` object (`null` without `--verify`). It carries the check name, status, agent outcome, exit code, signal, timeout, duration and cleanup only, never argv, paths or output. Preview reports the pinned program path and argument count and never runs it.
- **Stop/repair**: a single run never repairs, retries or re-prompts after a failed gate, and never executes model-suggested commands. In sequences (P5.2), a step whose gate is not `passed` stops dependent steps. Any continue-on-failure option must be an explicit P5.1 choice. A bounded repair iteration belongs to Ralph and is decided in P6.1.
- **Evidence/limits**: [P5.5 evidence](docs/evidence/p5-5-verification-gates.md). Check output is not captured or persisted; durable output references arrive with P5.3 state. Output on stderr is operator-command output, not harness diagnostics, and may contain anything that command prints.

## 2026-11-03 — D044: Sequence inputs, fresh-context steps, stop-on-failure and explicit resume

- **Context**: P5.1 fixes what P5.2 (ordered execution) and P5.3 (durable resume and inspection) implement. D043 already fixed the gate; WORKFLOWS states the behavioral requirements. No scheduler, queue or database is introduced; the invocation's mode stays authoritative.
- **Commands**: `ah sequence run DIR [options]`, `ah sequence resume RUN_ID [--retry|--accept] [options]` (the two choices together exit 2) and read-only `ah sequence show [RUN_ID]`. Options are the `single` coding options (`--project`, `--config`, `--mode`, `--model`, `--agent`, `--permissions`, `--timeout-secs`, `--no-sync`, `--verify`) plus `--preview` for `run`; prompt sources reject. `resume` takes its project, config and folder from the record, so `--project`/`--config` reject there. `--output jsonl` rejects for every sequence command in Phase 5: D039's contract ends one invocation with one `result` record, and a multi-step record contract waits for demand.
- **Folder snapshot**: DIR is read once, non-recursively, before any key lookup, runtime, network check, lock or state write. Entries whose names start with `.` are ignored. Every other entry must be a regular file (no symlink, directory or special file) named `N-slug.md`, where `N` is 1–6 ASCII digits and the slug matches `[A-Za-z0-9][A-Za-z0-9._-]*`, at most 128 bytes in all; anything else exits 2, so a misnamed step is never silently skipped. Steps are ordered by the numeric value of `N`; two steps with the same value (`1-a.md`, `01-b.md`) exit 2. 1–256 steps; an empty folder exits 2. Each file follows the existing prompt rules (UTF-8, at most 1 MiB, non-empty body, D040 slash-command refusal), and the snapshot holds at most 16 MiB. Execution uses the in-memory snapshot, so edits made by a step's agent to later prompt files do not affect the running sequence. Each step's identity is its file name plus the SHA-256 of its raw bytes.
- **Step metadata**: an optional frontmatter block, opened by a first line of exactly `---` and closed by the next `---` line, at most 16 KiB, parsed with the strict YAML rules of D036 (no tags, no type coercion, duplicate or unknown keys exit 2). Only two keys exist. `agent: NAME` selects `agents/NAME.md` for that step under D037/D038; when `--agent` is also given, a different metadata name exits 2 rather than overriding the invocation. `verify: NAME` names a declared check for that step; it requires the invocation's `--verify`, which in a sequence authorizes gating every step and names the default check, so metadata can substitute another declared check (for example `build` for a test-writing step) but can never disable the gate. Metadata cannot set mode, model, permissions, timeout, sync or any command; D003's per-prompt mode stays deferred. All metadata is validated, and every referenced agent and check resolved and pinned, for every step before step 1 launches.
- **Context policy**: every step is a fresh single run, with a fresh private runtime, session, grants and full preflight, through the same application service, agent resolution, route policy, managed sync and D034 fallback. Continuity between steps is the project filesystem and the step's own prompt only; no transcript, response, session or grant crosses steps. Route and agent restrictions are revalidated per step and per attempt. `--timeout-secs` bounds each step attempt; there is no whole-sequence deadline in Phase 5.
- **Failure policy**: strictly linear. A step completes only when its agent outcome is success and, if gated, its check `passed`. Any other result (rejected, failed, cancelled, uncertain, or a gate that is `failed`, `timed_out`, `error` or `cancelled`) stops the sequence; later steps stay `pending`. A signal between steps stops before the next launch (exit 3). Phase 5 offers no continue-on-failure option. The sequence exit is the stopping step's D024/D043 exit, or 0 when every step completed.
- **State location and layout**: `$XDG_STATE_HOME/agent-harness/` when that variable is an absolute path; otherwise `$HOME/.local/state/agent-harness/`, and only in that fallback does a missing or relative `HOME` exit 2 before launch. The root must lie outside the canonical project, so a project `git clean` or agent edit cannot remove it by accident. Runs live at `sequences/RUN_ID.json`, locks at `locks/PROJECT_KEY.lock` (SHA-256 of the canonical project path). Directories are created 0700 and files 0600; symlinked or non-directory components exit 2. `RUN_ID` is `sYYYYMMDDTHHMMSSZ-` plus 8 lowercase hex characters from `/dev/urandom`, and that grammar is checked on input before any path is formed.
- **Record content (schema `v: 1`)**: run ID, timestamps, canonical project, folder and config paths, run status, and ordered steps (name, SHA-256, effective agent and check, status). Each step attempt records its number, reason (`initial`, `resume`, `retry` or `accept`), timestamps, input SHA-256, agent-definition SHA-256, check identity (name, pinned program path, SHA-256 of argv), route, model, fallback target, permissions profile, timeout, agent outcome, exit, verification object (D043 fields) and the per-backend attempt summary of the D039 result (`launched`, `prompt_submitted`, `backend_stop`, `cleanup_confirmed`, `grants`, `tool_events`). The record never holds prompt text, responses, check output, argv text, environment names or key values; check output stays on stderr only. Paths are retained because resume needs them, and the file is private to the user. At most 32 attempts per step and 4 MiB per record; a resume that would exceed either exits 2.
- **Atomicity and crash windows**: each write creates a same-directory temporary file exclusively (0600), writes, fsyncs, renames over the record and fsyncs the directory, as in D025. The run writes the record before step 1, marks a step attempt `active` before launching its runtime, and writes its terminal result before the next step. Failure of a write before a launch stops with exit 1 and nothing launched; failure after an attempt returns exit 4, because the durable record may not reflect what happened. An attempt found `active` without its lock held is `interrupted` and treated as uncertain; no write marks the submission boundary.
- **Concurrency**: `run` and `resume` hold a nonblocking advisory lock on the project's lock file for their whole duration; contention exits 2 before any launch, matching D025. At most one sequence acts on a project at a time; from Phase 6 the lock is shared with Ralph runs (D045), so at most one sequence or Ralph run does. Single runs do not take this lock; running one concurrently in the same project is unsupported and documented. `show` takes no lock and relies on atomic replacement; it reports an `active` record whose lock is free as `interrupted`.
- **Resume**: a new `run` never resumes implicitly; it starts at step 1 and lists unfinished runs for the project on stderr. `resume` re-reads the folder. Completed steps (`succeeded` or `accepted`) must still be the leading steps with identical names and hashes in the same order, or resume exits 2 naming the first mismatch. Remaining steps are re-snapshotted, so a failed step's prompt can be edited and steps can be added, removed or appended after the resume point. Route options resolve afresh from the current config and this invocation, as for any new invocation. Each attempt records its own identity and the human output reports what differs from the step's previous attempt, so a changed input never resumes silently as the same step. The stopping step is the first incomplete one. If its last attempt never crossed the submission boundary (rejected before launch, or failed/cancelled with `prompt_submitted` false on every backend attempt), resume retries it with reason `resume`. Otherwise (a submitted prompt, any uncertain or interrupted attempt, or a gate that did not pass) resume exits 2 unless the caller chooses: `--retry` runs a new agent attempt; `--accept` runs no agent turn, and a gated step runs its current check and completes as `accepted` only if it `passed`, while an ungated step is recorded `accepted` by the operator and never labeled verified. A step whose last attempt had a check stays gated from the record: `--accept` then requires `--verify`, and the step's effective check name must equal the recorded one, or it exits 2. That check is re-pinned from the current config and must keep the recorded identity: a changed pinned program or argv hash exits 2 on bare resume, `--retry` and `--accept` before anything launches or any record is written (Phase 6 review R06-02); restore the check or start a new run. A step whose last attempt was ungated is gated only if the current resolution gives it a check. An `accept` attempt is always appended. If its check does not pass, the step takes that result (`failed` for `failed`/`timed_out`/`error`, `cancelled`, or `uncertain` on unconfirmed check cleanup), the run stays stopped, the exit follows D043 (1, 3 or 4), and a later resume again needs a choice. A run with no remaining steps exits 0 without launching. Earlier attempts are never rewritten or deleted.
- **Compatibility and retention**: records are strict: unknown fields or an unparsable file exit 2, and a `v` other than 1 exits 2 without rewriting. Any schema change bumps `v`, and its migration rule is decided with that change. Records are kept until the user deletes them; Phase 5 adds no pruning command. Deleting a run file while no sequence holds the project lock is safe.
- **Preview**: `run --preview` resolves the snapshot, metadata, agents and pinned checks, and prints the ordered steps with each step's agent, check, prompt size and any refusal. It reads no state, takes no lock and stays network-free and write-free.
- **Not selected**: continue-on-failure, parallel or DAG steps, shared runtime sessions, recursive folders or other file types, per-step mode/model/permissions, sequence machine records, a pruning command, a whole-sequence deadline, and persistence of the submission boundary. R04-REC1 (tool kind on activity lines) is not needed for sequence semantics; P5.4 re-evaluates it from real use.
- **Dependency**: SHA-256 needs a new pinned dependency (RustCrypto `sha2`, MIT/Apache-2.0). P5.2 evaluates its version, license and Rust 1.88 compatibility with its first consumer, as D036 did for YAML.
- **Validation**: P5.2 tests ordering, input and metadata errors, conflicts and dependent-step stopping; P5.3 tests crash windows, competing writers, changed inputs and schema, and cancellation; P5.4 exercises a real interrupted task.
- **P5.3 implementation notes** (within this decision; detailed in [WORKFLOWS](docs/WORKFLOWS.md#durable-records-and-resume)): the record's v1 field names and the `argv_sha256` encoding are fixed there. Symlink and privacy checks cover the harness-owned `agent-harness/`, `sequences/` and `locks/` directories and lock files, not the user's ancestors: a reused one not owned by the user or with group/other access exits 2 and is not repaired. An attempted stopping step that was removed, even by truncating the folder to the completed prefix, exits 2 rather than reporting nothing remaining. The lock file names its holder run, and `show` uses a momentary nonblocking shared probe to tell `active` from `interrupted`; it holds no lock. `resume` resolves only the remaining steps, records stale `active` attempts as `interrupted`, and refuses if the record changed before it took the lock. The 4 MiB bound is enforced per write (a write failure: exit 1 before a launch, 4 after) rather than predicted before a resume. `show` accepts `--project PATH` for its listing.

[Study evidence](docs/evidence/p6-1-ralph-study.md) covers ralph-orchestrator and ralph-rs. Both re-send a stable prompt and keep progress in files. It is read once per invocation, before any key lookup, runtime, network check, lock or state write. Its identity is the canonical path plus the SHA-256 of its bytes. `--agent`, model, route, permissions and the check are resolved and pinned once per invocation, as for a sequence step.
- **Fresh-context handoff**: every iteration is a fresh single run, with a fresh private runtime, session, grants and full preflight, through the same application service, agent resolution, route policy, managed sync and D034 fallback. Nothing from earlier iterations' transcripts, responses, sessions or grants is passed on. The prompt sent is a fixed harness header followed by the snapshot. The header holds only enumerated values from the harness's own record: the iteration number and the bound; the previous iteration's agent outcome, whether it claimed completion, and its check status (or "none" for the first iteration of the run); the check name; and an instruction stating the completion marker and that the harness runs the check. It never includes response text, check output, file content or paths. Task progress belongs in project files that the prompt tells the agent to read and update. The harness does not create, read or interpret them. Exact header wording is a P6.2 detail, and the record keeps the SHA-256 of the full text sent.
- **Completion signal**: completion needs two things from the same iteration. First, a claim: the iteration ended in backend success, its final response was delivered after `end_turn` and confirmed cleanup, and the last non-empty line of that response, with trailing ASCII whitespace removed, is exactly `AH-RALPH-COMPLETE`. Second, the pinned check, run under D043 after that iteration, returns `passed`. The response is otherwise untrusted and is not stored.
- **False and stale signals**: a claim whose check does not pass is a rejected claim, recorded with the check status. Text that only contains the marker somewhere else is no claim. A response from an iteration without backend success is never inspected, and its claim is recorded as `null`. A claim never carries over to another iteration or invocation. DONE files, checklists, progress files, commit messages and clean exits are never signals. The check runs only after a claim, so a check that would already pass without a claim does not complete the loop. An operator who wants the loop to end as soon as the check passes writes the prompt that way. The check is the operator's definition of done, so a weak check limits what completion means; D043's trust and pinning rules are unchanged.
- **Iteration outcomes**: the loop continues to a new iteration only after backend success with either no claim or a rejected claim whose check ended `failed` or `timed_out`; that next iteration is the bounded repair D043 assigns to Ralph. Every other result stops the loop with its D024/D043 exit and status `stopped`. That covers rejected, failed, cancelled and uncertain agent outcomes, and a check ending `error`, `cancelled` or with unconfirmed cleanup. No backoff, consecutive-failure budget or automatic replay exists, because D031/D044 already forbid launching again after a submitted non-success. A signal between iterations stops before the next launch (exit 3) and leaves the run resumable.
- **Bounds**: `--max-iterations` is 1–100, default 10. It counts every recorded agent iteration of the run across invocations; an `accept` iteration runs no agent turn and does not count. Reaching it without completion ends the run `exhausted`, exit 1. `--max-runtime-secs` is 1–86400, default 3600, and bounds wall time per invocation from the start of the first iteration. It is checked before each launch and caps each iteration's agent deadline at the lesser of `--timeout-secs` and the remaining time. An exhausted bound at an iteration boundary ends the run `exhausted` (exit 1). A deadline reached during a turn is that attempt's D024 deadline outcome (exit 3 or 4), and the run is `stopped`. A check that has started is not cut short: it keeps its own D043 timeout. A run can therefore exceed the wall bound by at most one check timeout plus the existing cleanup and output allowances. There is no "unlimited" value.
- **Usage**: there is no cost or token bound. OpenCode `usage_update` cost is a backend report that may be absent, and enforcing it would mean cancelling mid-turn with uncertain effects. Each backend attempt in the record keeps its D039 usage object. `show` gives a cost total only when every submitted attempt reported a cost in one currency, and otherwise reports the total as unknown. That total is a backend report, not billing.
- **State and concurrency**: the D044 store and atomicity rules apply. Ralph records are `ralph/RUN_ID.json` with `RUN_ID` = `r` plus the D044 timestamp and random grammar. `run` and `resume` take the same per-project lock as sequences, so at most one sequence or Ralph run acts on a project; contention exits 2 before launch. Records (`v: 1`, strict, unknown fields exit 2) hold the run identity, timestamps, canonical project, prompt and config paths, status (`active`, `stopped`, `completed`, `exhausted`), the current iteration bound, and each invocation's start, reason and wall bound. They also hold ordered iterations. Each iteration keeps the D044 attempt fields (number, reason, status, timestamps, agent SHA-256, check identity, route, model, fallback, permissions, effective timeout, agent outcome, exit, verification, per-backend summary) plus `prompt_sha256` (file), `input_sha256` (header plus file), `claim` (true, false or null) and the per-backend usage object. Iteration reasons are `initial`, `continue`, `resume`, `retry` and `accept`. The record holds no prompt or header text, responses, check output, argv text, environment names or keys. Limits are 100 recorded iterations (agent and `accept` alike) and 4 MiB per record. The loop checks the recorded count before every append; at 100 the run ends `exhausted` and later resumes refuse. No path writes a record that its strict reader would refuse (R06-01). An iteration is marked `active` before launch and written before the next launch. An `active` iteration whose lock is free is `interrupted` and treated as uncertain.
- **Resume**: `run` never resumes implicitly; it lists the project's unfinished Ralph runs on stderr. `resume` re-reads FILE from the recorded path. A changed prompt is allowed, recorded and reported as a changed identity, because steering the task between invocations is legitimate. The check must have the recorded name. It is re-pinned and must keep the last recorded check identity (pinned program and argv hash); otherwise resume exits 2 before any launch or write, whatever the choice (R06-02). A changed definition of done needs a new run. Route options resolve afresh. A `completed` run exits 0 without launching and without reading FILE or the config (R06-07). Otherwise the last iteration decides. If it never submitted a prompt (`prompt_submitted` false on every backend attempt), or it ended in backend success without a check that stopped the run, bare resume launches the next iteration. If the run's counted agent iterations have reached its iteration bound, resume first needs `--max-iterations` greater than that count (exit 2 otherwise), and the new bound is recorded. A run exhausted only by wall time resumes under its recorded iteration bound, because each invocation has its own wall bound. `--max-iterations` given on any resume must be greater than the counted iterations and at most 100. In every other case (a submitted non-success, an uncertain or interrupted iteration, or a check that ended `error`, `cancelled` or with unconfirmed cleanup) resume exits 2 unless the caller passes `--retry` or `--accept`. `--retry` launches a new iteration and is allowed wherever a new iteration is. `--accept` needs a last iteration that may have had effects. It runs no agent turn, appends an `accept` iteration and runs the check. A `passed` check completes the run with that iteration `accepted`, an operator decision in place of the claim. Otherwise the run stays stopped with the D043 exit. Earlier iterations are never rewritten or deleted.
- **Cancellation**: SIGINT/SIGTERM during an iteration follow the single-run and D043 cancellation paths (exit 3, or 4 when uncertain), and the run is `stopped`. Between iterations, the harness exits 3 before the next launch. Stop-request files are not supported, because the agent can write project files.
- **Preview**: `run --preview` resolves FILE, agent, route and the pinned check. It prints the prompt size, agent, check, both bounds and the iteration-1 header, reads no state, takes no lock and stays network-free and write-free.
- **Output**: each iteration's human response goes to stdout, newline-terminated and flushed when its turn ends (as for sequence steps). Human stderr reports each iteration's start, outcome, claim and check status, and the terminal reason: `completed`, `exhausted` (iterations or time), or the stopping outcome.
- **Not selected**: model-only, file-based or exit-based completion; an unverified Ralph mode; cost/token budgets; consecutive-failure budgets, backoff or cooldown; stale-loop or no-progress detectors and R05-REC1 tool-kind counters (neither is needed for completion semantics; both are re-evaluated from P6.4 use); harness-owned progress files; feeding check output or responses to the next iteration; persistent/idle loops; multiple roles per loop; parallel loops; Ralph machine records; a pruning command.
- **Validation**: P6.2 tests fresh runtime context and private state per iteration, header content and identities, durable records, interrupted iterations and the shared lock. P6.3 tests a claim with a failing check (continues), the marker elsewhere in a response (no claim), a stale claim and a DONE file (ignored), a passing check without a claim (continues), exhausted iteration and wall-time bounds, cancellation during and between iterations, check `error` (stops) and resume choices. - **P6.3 implementation notes** (within this decision; detailed in [P6.3 evidence](docs/evidence/p6-3-ralph-completion.md)): a rejected-claim iteration is recorded `failed` with exit 1 and its check status, keeping `agent_outcome: succeeded`, as for a gated sequence attempt; the run continues. One rule decides completion, continuation or stop from the recorded iteration, and resume and `show` reuse it. `--verify` on resume must match the check recorded on the run's iterations; a run with no iteration has none recorded. The first resumed iteration reports changed identities (prompt, agent, check name/program/argv, route, model, fallback, permissions); the timeout is omitted because the wall bound caps it. An `accept` iteration sends no input, so its `input_sha256` is the SHA-256 of the empty string. 100 recorded iterations refuses every resume choice.

The 100-recorded-iteration limit is checked before each append, and the store refuses to encode a record that fails its own consistency rules (R06-01). An `accept` iteration still records the D044 attempt fields as resolved at accept time. Its change report covers only prompt and check identity, and `show` marks its route, model, fallback and permissions as not applicable, because no agent turn ran (R06-05).
