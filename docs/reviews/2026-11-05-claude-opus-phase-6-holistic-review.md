## Integrated assessment

### Architecture and ownership

`ralph` is a thin coordinator, as DESIGN intends. It owns the snapshot, header, the `next`/`after`/`plan` decisions, the session writer, `show` and preview. It reuses `single::launch` for execution, `verify::gate` for the check and `state` for the store. The generic `Stored` trait and `Kind` let one store, lock and atomic-write implementation serve both workflows without duplicating the safety code; the sequence suites still pass unchanged apart from the lock message. `drive` behind an injectable launcher is a good testability seam. No dependency was added.

One layering inversion: `progress::deliver` calls `crate::ralph::claims` on every delivered response, including plain `ah single` and sequence steps (C06-06). It is harmless today, but it makes the output layer depend on a workflow module.

### Routing, permissions and fallback

Ralph adds no route surface. Mode, model, agent, permissions and the check are resolved once per invocation through `Invocation::step`/`resolve` and checked by `single::supported`. The fallback request receives the same header and deadline (`ralph.rs:1010–1013`), and claim detection works across a fallback because `Progress` is shared. That code is correct by inspection but untested (C06-03). Resume re-resolves route options from the current config and flags, and reports changes. Narrowing (forgetting `--permissions trusted`) is safe. Widening needs an explicit operator flag. Both match D044.

### Completion, bounds and recovery

The completion rule is strict and conservative. `claims()` accepts only an exact final line, and a claim is read only after `Exit::Success`. The check runs only after a claim, so a pre-passing project cannot complete a run without one. `may_have_effects()` treats every accept iteration as possibly effectful, so a failed accept still needs an explicit choice, and a second `--accept` stays available. The wall bound is honest: an iteration in flight when the wall deadline arrives ends as its own deadline outcome and the run is `stopped`, not `exhausted`, as D045 says. With as little as 1 s left, the harness still launches an iteration that cannot do useful work (R06-REC2).

The gaps are in record integrity (C06-01) and in how far resume trusts the current config's check (C06-02).

### State and concurrency

Ralph records share the D044 store, private-mode checks, atomic create/replace and the per-project lock. A running Ralph refuses a sequence and vice versa, as `ralph.py` and `sequence_state.py` show. Resume plans on a copy, takes the lock, then refuses if the record changed. The P6.2/P6.3 limits are stated honestly: a concurrent `ah single` goes undetected, the submission boundary is not persisted, v1 has no migration and there is no pruning. `Store::write` encodes and size-checks but does not apply `consistent()`, which is how C06-01 can persist a record that `read` refuses.

### Tests and evidence

The tests assert observable behavior: prompts that reached the runtime, record bytes and modes, checker invocations and exits. Root tests number 120 (24 library tests plus 96 integration tests), and `ralph.py` passes. The gaps are specific. There is no Ralph case under local-first or cloud-only, and none with `--agent` offline (P6.4 covers `--agent` live on local-only only). No case changes a check's program or argv between invocations. No case pushes recorded iterations past 100 with an accept in the record.

### Operations and documentation

WORKFLOWS carries the full Ralph contract and the P6.4 use guidance. OPERATIONS has no Ralph runbook and still calls Ralph guidance prospective. Its sequence runbook says only one *sequence* can hold a project, although the lock is now shared with Ralph. The other summaries have drifted too (C06-07).

## Recommendations (not defects)

- **R06-REC1 — tool-kind counters (R05-REC1, carried forward).** P6.4 F1 shows per-kind counts (edits versus commands) would have told the operator whether a long iteration was still changing files. Keep it as a backlog candidate. It informs, but cannot prove, the absence of effects.
- **R06-REC2 — minimum launch budget.** `next()` launches an iteration whenever at least 1 s of wall time remains. A near-empty budget yields a deadline `stopped` iteration (and, after submission, a required `--retry`/`--accept`) instead of a clean `exhausted`. Consider exhausting when the remaining time is below a small floor, for example a fraction of `--timeout-secs`, and record the rule in D045.
- **R06-REC3 — header stopping instruction.** The header could say, in fixed text, to stop and claim as soon as the task's stated checks pass. This complements the WORKFLOWS guidance; per P6.4, the task file's own stopping rule remains the primary control.
- **R06-REC4 — resume wall-bound default.** `resume` defaults `--max-runtime-secs` to 3600, not to the run's last recorded invocation bound. That is consistent with "each invocation has its own wall bound", but an operator who started with `--max-runtime-secs 600` may not expect an hour on resume. Either inherit the last bound or print the effective bound prominently (it is printed today in the loop's first note).
