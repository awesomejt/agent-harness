# Execution contract

Status: design contract, not a published Rust API or wire schema. See [architecture](ARCHITECTURE.md), [configuration](CONFIGURATION.md), and [workflow state](WORKFLOWS.md). Phase 1 chooses transport/permission handling, Phase 2 fixes initial request/exit behavior, and Phase 4 versions machine-readable output.

## Request resolution

Resolve one project path, prompt source, operational mode, runtime, and model alias, plus an optional canonical agent (`--agent`, D037: selection, model precedence and preview; named execution refuses until P4.3 enforcement). Record whether each effective choice came from the invocation or configuration. Accept inline text, a file, or stdin; reject conflicting sources and empty content before launching work. D024 and [the first-slice configuration contract](CONFIGURATION.md#selected-invocation-and-preview-syntax) fix flag names, limits and defaults. A missing input must not unexpectedly launch an interactive coding session in CI.

Keep primary versus specialized role separate from route and runtime. A request to review without writes must become enforceable runtime restrictions; advisory system text is insufficient.

The proposed Rust domain model and supervisor ownership are in [DESIGN.md](DESIGN.md); lifecycle and route diagrams are in [ARCHITECTURE.md](ARCHITECTURE.md). Internal type names do not establish a public JSON schema.

## Lifecycle

Conceptual lifecycle (names are not serialized enums): resolve -> validate -> preview, or prepare managed configuration -> launch -> active -> cleanup -> terminal outcome (succeeded, failed, cancelled, uncertain). Every active attempt passes through cleanup, including successful, failed, timed-out and cancelled attempts. Validation rejection or a known spawn failure without a child can terminate before active work; ambiguous startup or cancellation during launch still requires cleanup and an outcome reflecting uncertainty. Preview ends without executing or modifying configuration. Retrying creates a new attempt linked to the original run rather than rewriting history.

A prompt acknowledgement, text chunk, clean stdout EOF, model completion, child exit, and verified task completion are different events. The adapter must identify the backend's actual terminal condition and await cleanup. Workflow verification is a separate result from successful agent execution.

## Progress and outcome

Every invocation has a run identity; every launched attempt has its own identity and selected route/runtime/model. Show elapsed time, useful activity, permission requests when applicable, and a final outcome. Preserve backend session identity when reported without assuming cross-runtime continuity. Report token/cost usage only with provenance and units; unavailable metrics remain unknown, not zero.

Outcomes distinguish validation rejection, launch failure, runtime/provider failure, success, cancellation/deadline, and uncertain completion after an interrupted attempt. Include retry eligibility and possible side effects where known. Do not infer that absent tool events prove no tool executed after a transport failure.

Human diagnostics go to stderr when stdout carries a final response or structured records. The Phase 4 machine contract must specify envelope version, IDs, timestamps/order, event types, optional provider fields, redaction, and a terminal record. Do not expose chain-of-thought as a required normalized field. Bound output buffering and document truncation rather than silently dropping completion or permission events.

D024 fixes numeric exits: 0 = successful backend turn plus confirmed cleanup; 1 = launch/runtime/provider/output failure with known outcome; 2 = rejected input/configuration/unsupported capability; 3 = cancellation/deadline with known terminal outcome and confirmed cleanup; 4 = uncertain completion or cleanup. Uncertainty overrides other outcomes, even after a backend success marker. Cancellation is known only with affirmative evidence of termination/effects; missing tool events do not prove it. A successful agent turn does not mean tests passed. These values are represented in the validation library; P2.2/P2.4 implement runtime classification. Uncertainty takes precedence when cancellation or timeout may have left side effects; report that uncertainty explicitly on stderr in Phase 2 rather than waiting for Phase 4 machine records. Later structured-output additions must preserve documented shell behavior.

## Adapter capability contract

Record tested runtime version, launch interface, model/effort mapping, project/rule loading, progress/terminal semantics, tool and permission restrictions, headless behavior, session behavior, usage reporting, and cancellation/descendant cleanup. Mark capabilities as tested, unsupported, or unverified; a capability declaration alone is not evidence.

Resolve restrictions before model work. If a runtime cannot enforce the requested constraint or route, refuse execution. In particular, inherited models, helper/subagent models, skills, MCP tools, and runtime fallback must not bypass routing/permissions. This is configuration and integration policy, not a claim of OS/network sandboxing for arbitrary commands.

Runtime-managed skills, MCP, context selection, compaction and caching remain runtime responsibilities. The harness reports relevant limitations and preserves restrictions; it does not implement those subsystems for MVP.

## Permissions and headless operation

P1.6 fixes the experiment policy in [D020](../DECISIONS.md#2026-11-01--d020-fail-closed-experiment-permissions). The dependency-free `permission` module and synthetic request fixtures exercise this policy; they are not an ACP implementation or proof of live runtime enforcement.

| Action / policy | Experiment behavior |
|---|---|
| File reads, edits, shell commands (including tests), network, external/MCP tools, unknown actions | Deny by default, including inside the disposable project. Project location alone grants nothing. |
| Explicit trusted grant for one fully described request | Select only an advertised, adapter-verified allow-once option for that exact request. |
| Allow-always, category/wildcard grants, inherited permissive defaults | Unsupported; never substitute these for allow-once. |
| Prompt / interactive approval | Unsupported for this experiment, even with a TTY. Refuse a policy requiring prompting before launching model work. |

Each attempt starts with a fresh default-deny policy. A trusted experiment driver may supply a grant after checking session authorization, requested tool arguments and scope; backend text and project instructions cannot supply grants. Bind the grant to the attempt-unique request ID, complete action descriptor (including arguments/scope) and advertised options. Consume it on the next request, including mismatch or malformed input. Changed/repeated requests need new authorization; no grants carry into retries or fallback. The Rust fixture accepts an already reviewed normalized request, not arbitrary backend labels as trusted semantics.

For a valid ungranted request, select an advertised, adapter-verified denial option immediately. If none exists, respond with protocol cancellation; if cancellation is unsupported, stop the attempt. Empty request/action/option identities or duplicate option IDs are malformed: refuse and fail the attempt. Never invent option IDs or infer semantics from display labels. There is no stdin read, TUI, approval wait or implicit timeout approval in the policy function.

Before a live P1.2 prompt, the adapter must show effective policy/grants, map actual transport option kinds, and verify that runtime auto-allowed tools, inherited settings, filesystem/terminal callbacks and external tools cannot bypass the selected restrictions. Configure deny/ask behavior as needed so granted operations pass through enforcement. A runtime that cannot enforce the policy is refused before model work. Permission-response send failures stop work and enter cleanup; do not retry with broader permissions. Lost transport or uncertain tool activity produces an uncertain outcome under the lifecycle contract. P1.2 establishes transport feasibility; [P1.3 evidence](evidence/p1-3-lifecycle.md) verifies live denial/cancellation, project instruction loading, actual outbound alias selection and macOS process-group cleanup in a standalone Rust SDK experiment. This does not implement the production supervisor or broaden platform support. The experiment policy does not add CLI/config syntax or claim an OS sandbox.

Treat project instructions, prompt files and backend output as data/instructions within the selected trust scope, not authorization to change mode or credentials. The harness is not a security sandbox around a coding runtime and cannot promise containment of arbitrary shell tools merely from a project path.

## Failure and fallback

P3.1 selects the following policy; P3.3 implements the local-first coordinator that applies it. A classification requires reliable structured, adapter-specific evidence; raw error text, HTTP-like substrings, absence of tool events, and missing acknowledgements are insufficient. If evidence is unavailable or contradictory, classify as unknown and stop. The current ACP adapter does not reliably distinguish provider authentication, rate limits or transport errors, and must not infer them from generic failures.

| Failure, established before prompt submission | Automatic native fallback |
|---|---|
| Invalid input/configuration, missing credentials, or unsupported constraint | Stop; correct the request or configuration. |
| Authentication/authorization failure | Stop; correct credentials or access. |
| Confirmed service/model unavailable, rate limit, or transport failure | Eligible only if all guards below hold. |
| Runtime/protocol/permission failure, unknown cause | Stop; inspect diagnostics. |
| User cancellation or deadline | Stop, even if another failure also occurred. |

Eligibility requires `local-first`, a configured native target independently validated to enforce the same required project, mode and permission constraints, confirmed process **and private-state** cleanup, an unexpired overall deadline, and no cancellation. The supervisor must affirm that submission was never attempted; set the submission boundary before handing the prompt to transport, because failed sends can still deliver. If no coding attempt was launched, cleanup is confirmed only when all resources actually created have been verified cleaned. Project configuration writes may already have occurred and are not rolled back. Only the original prompt and explicitly required request context may be sent; no backend transcript, session, permission grants or implicit context cross routes. Fallback creates a distinct linked attempt with fresh grants. No automatic same-route retry is permitted; at most one native fallback attempt is permitted per invocation, with no further fallback. Both attempts share the original active deadline; do not reset it. Each cleanup uses its existing finite cleanup budgets. Preflight requests may have occurred even when the coding prompt was never submitted.

Once prompt submission was attempted, no automatic replay or fallback is permitted, including after a known failure, cancellation, rate limit or terminal response. A missing trustworthy terminal response or unconfirmed cleanup remains uncertain (exit 4); even a known terminal failure or cancellation can have effects. Inspect project changes and external effects before deciding manually whether to issue a new invocation. A manual invocation is a new run and does not imply rollback or safe replay. Output-delivery failure after a successful turn also cannot authorize replay. Existing exit precedence remains unchanged.

The decision function and fixtures in `src/recovery.rs` and `tests/recovery.rs` exercise these guards. P3.3/D034 connects them to execution: in local-first, the only evidence source is a bounded TCP reachability check of the LiteLLM endpoint, made before any local runtime, private state, preflight or project write exists. An unreachable endpoint is `Transport` with affirmative `NotAttempted` submission, so `decide` permits the one configured native attempt; a reachable endpoint runs the local attempt, whose ACP failures remain unclassified and stop. local-only (including D033 group references) and isolated native cloud-only (P3.2/D032) never automatically retry or fall back. See [local-first configuration](CONFIGURATION.md#local-first-route-p33--d034). Native setup checks the pinned runtime and embedded model catalog; authentication/service availability are not established by those checks. See [native configuration](CONFIGURATION.md#native-opencode-route-p32--d032).

## Process and project integrity

Drain stdout/stderr concurrently; test backpressure, oversized records, partial UTF-8/JSON, unexpected exits, ignored termination, and descendants holding pipes. Cancellation/deadlines apply to the process tree and cleanup as supported by the platform, with documented limitations.

Detect and report an existing dirty worktree without rejecting normal developer work. Preserve pre-existing edits and untracked files. The harness must not stash, reset, clean, commit, roll back, or create worktrees automatically. Runtime tool actions remain subject to its explicit permissions; document that distinction. A later diff summary must distinguish baseline user changes from attributed run changes or state that attribution is unknown.

P2.8 reports an advisory baseline on human stderr after runtime preparation and before runtime preflight, project sync or the coding prompt. The fixed `/usr/bin/git` runs `status --porcelain=v1 -z` with optional index locks and fsmonitor disabled, global/system Git config disabled and inherited Git environment cleared. A bounded effective-config inspection (including included files and worktree config) runs first; any `filter.*` setting or incomplete inspection skips status and reports an unavailable baseline, preventing configured clean/process filter execution under the observed configuration. Both subprocesses share the two-second observation bound; each has a 1 MiB output cap and existing cleanup allowances. Avoid concurrent config edits, which can race inspection and status. Global-only filters are intentionally not loaded, so counts may differ from a normal Git invocation in projects that rely on them. Counts cover the containing repository (including files outside a selected subdirectory), with staged and unstaged counts overlapping for a file changed in both; untracked files are enumerated and ignored files/submodule contents are excluded. Filenames and Git stderr are never printed. A two-second/1 MiB status bound produces an explicit unavailable baseline on timeout, overflow, missing Git, non-repository or Git error; that observation does not reject normal coding. Unconfirmed Git process cleanup returns uncertainty and prevents runtime launch. System Git requires macOS Command Line Tools; without them, the `/usr/bin/git` shim may display an installation prompt before reporting unavailable. The active deadline includes observation; existing bounded cleanup allowances still apply. Preview performs no Git observation and retains its no-subprocess contract.

This is an observation, not a snapshot for rollback, a concurrent-edit lock, or attribution of later changes. Invalid inputs/plans or failure to prepare the runtime can stop before observation. Harness setup may persist its managed config/receipt/lock even when coding later fails or is cancelled; those writes follow the separate project transaction contract. The harness never restores baseline files or modifies the Git index/refs, ignores, or commits. Explicitly authorized runtime file/shell actions may alter pre-existing changes or Git state; success and cancellation do not undo them. Inspect project effects before retrying uncertain work.

## Selected Phase 1 transport and production handoff

D023 selects OpenCode ACP stable protocol 1 over stdio with SDK 3.6.0 on caller-owned Tokio pipes. The [acceptance preparation](evidence/p1-5-integration-acceptance.md) records exact tested versions/capabilities. `end_turn` establishes backend turn completion; it does not prove verification or cleanup. A malformed/wrong-session callback or failed permission response marks the attempt failed even if the backend subsequently returns `end_turn`. Session cancellation is separate from SDK request cancellation and must be observed or escalated within a bound.

The experiment proves default-deny callbacks and forced Unix group cleanup on macOS only. It discards stderr, limits total wire bytes to 2 MB and assistant text to 100 KB, uses a 180-second overall bound and a 15-second cancellation response bound, then a fixed 300 ms TERM grace and a five-second reap bound. These are probe settings. P2.4 must define/test production budgets, bounded stderr/event handling and descendant verification, including after the leader exits; unconfirmed cleanup cannot yield success. Production graceful flush is unverified, detached groups remain outside containment, and no remote-inference cancellation guarantee follows from local cleanup. P2.1 must specify useful coding permissions and outcome/exits; P2.2 must enforce that contract and verify minimum bounded cancellation/cleanup before its first real coding prompt. P2.4 completes production supervision, progress/outcome reporting and adversarial hardening before release. Phase 2 remains gated on P1.7.

## P2.2 minimum production supervision (historical baseline)

The macOS adapter owns every version/config/agent/ACP subprocess in a new Unix process group. Preflight captures at most 1 MiB with a per-check maximum of 30 seconds inside the overall request deadline; stderr is discarded. ACP traffic is capped at 8 MB, assistant text at 1 MB and permission/tool identities at 4096. stdout receives buffered assistant text only after backend `end_turn` and confirmed cleanup; stderr identifies the route and safe outcome counters. P2.4 still owns ongoing progress, IDs, usage, richer bounded diagnostics and adversarial hardening.

Cleanup sends group TERM, waits up to 500 ms while the leader remains active, sends group KILL even after leader exit, and allows five seconds to reap the direct child. Bounded `/bin/ps` checks then confirm no live member of the original group (zombies count as terminated). Unverified cleanup overrides every outcome with exit 4. Detached sessions/groups and downstream inference are outside this guarantee; authorized shell commands are not OS-sandboxed. These budgets are a tested minimum, not a guarantee of graceful flushing.

A signal/deadline before prompt submission with confirmed cleanup returns 3. Once a prompt has been sent, interruption, protocol/callback failure or lost transport without a trustworthy terminal response returns 4, even when local cleanup succeeds. Known `cancelled` returns 3; `end_turn` plus cleanup returns 0; other known terminal reasons return 1. Raw provider errors are withheld. P2.2 uses forced bounded cleanup for active interruption; graceful ACP cancellation and more detailed failure classification remain P2.4. No outcome triggers automatic replay or fallback. Input/config/unsupported capability rejects use 2; spawn/output failures use 1 when no uncertain effects remain.


## P2.4 selected supervision and human output

P2.4 supersedes the preceding minimum budgets. Every `single` invocation reports a run ID and elapsed seconds on stderr; the one ACP attempt is identified by the pair `(run, attempt=1)`. Route/runtime/model and permission profile precede launch; escaped, bounded backend session identity follows session creation. Activity counters stream as assistant/tool notifications and headless permission responses arrive, with a five-second heartbeat during idle work. Backend text, tool arguments, reasoning, raw stderr and provider errors are withheld from diagnostics. stdout retains the final assistant response only after `end_turn` and confirmed cleanup. This human format is not the Phase 4 machine schema.

Stable ACP `usage_update` notifications, when present, report source-attributed context-used/capacity in tokens and valid nonnegative cumulative session cost with currency units. These are backend reports, not independently measured billing or per-turn token totals. Per-turn tokens remain unknown; missing reports/costs explicitly say unknown rather than zero. No unstable SDK feature is enabled. A terminal failure is reported separately from setup/launch failure, protocol/callback/output-limit violation, transport/provider loss, cancellation and response-delivery failure. Provider authentication/rate-limit details cannot be distinguished reliably through this interface and remain a generic runtime/provider/transport failure. No outcome permits automatic retry or native fallback.

On SIGINT/SIGTERM or the overall deadline, an active prompt receives `session/cancel` and has **five additional seconds** to supply an actual terminal prompt response. A cancellation ACK, text notification or EOF is insufficient. Before prompt submission, interruption can return 3 after confirmed cleanup. During active work, missing terminal evidence returns 4; confirmed `cancelled` returns 3, and a racing `end_turn` can still return 0 after cleanup. Cancellation preserves any already-applied project effects and makes no claim of rollback or stopped downstream inference. Further permission requests are denied after signal/deadline, including under `trusted`; earlier grants/actions may already be in flight.

All subprocesses drain stdout and stderr concurrently. Preflight retains its 1 MiB stdout and 30-second per-check bound inside the overall deadline. ACP retains an 8 MB total wire limit, 1 MB assistant response limit and 4096 permission/tool identities. Crossing a protocol/text/state limit terminates the attempt with an explicit diagnostic; active effects stay uncertain. Malformed/truncated protocol records, invalid UTF-8 and unexpected exit cannot establish success. stderr uses an 8 KiB drain buffer; no raw bytes are stored or printed, and the safe byte counter saturates at 1,048,577 (indicating more than 1 MiB).

Cleanup sends process-group TERM and waits up to **two seconds** for the direct child, then sends group KILL even if the leader has exited; direct-child reap remains bounded at five seconds. stderr drain completion gets 500 ms, then its task is aborted. Up to ten bounded `/bin/ps` inspections (one second each, with 100 ms spacing) verify no live original-group members; zombies count as terminated. Cleanup failure overrides every other outcome with exit 4. The two-second TERM grace allows cooperative runtime shutdown, but forced escalation is not called graceful. Detached groups and arbitrary shell side effects remain outside containment.

Human diagnostics use a dedicated OS thread and nonblocking 64-entry queue, with messages capped at 512 Unicode characters plus the fixed prefix. Repetitive activity is sampled and queue overflow is counted in the separately retained final summary. Permission/terminal protocol handling never uses this lossy queue. Final diagnostic drain gets **one second**; an unread/broken stderr may prevent delivery, but cannot block cleanup or change a known execution outcome. stdout delivery uses a separate thread with a **two-second** budget after cleanup; blocked/broken output returns 1 and can leave a partial response. CLI process exit ends blocked writer threads. These finite cleanup/output allowances are additional to the active/preflight deadline. File fsync/replace remains OS-bounded as documented in D026.


## P2.9 private runtime-state cleanup

D030 adds an explicit private HOME/XDG removal check after every prepared runtime path, including preflight failure and cancellation, before the invocation's final outcome. A separate OS worker performs recursive removal and verifies absence; the supervisor waits at most two seconds. If worker creation fails, removal is unattempted; there is no synchronous fallback because recursive filesystem I/O cannot be given the supervisor's wait bound. Worker failure, filesystem error, unconfirmed absence or timeout overrides the exit with 4 and a redacted warning that temporary state may remain. Process-group cleanup remains a separate check. A timed-out worker can continue until CLI process exit; no detached-writer containment or cleanup after abrupt termination is promised. Constructor failures retain best-effort removal before any coding work.

The final assistant response may already have been delivered after backend success and confirmed process cleanup; later private-state removal failure still returns 4. Honor the final exit rather than inferring success from stdout. Inspect retained `ah-runtime-*` directories in the system temporary directory deliberately; never apply automatic cleanup to the selected project. The immutable published `v0.1.0-alpha.1` artifact retains its earlier best-effort private-state removal behavior; this correction is in source for the next packaged version.
