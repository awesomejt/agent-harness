P5.1 fixes the sequence commands, inputs, failure policy, state and resume ([D044](../DECISIONS.md#2026-11-03--d044-sequence-inputs-fresh-context-steps-stop-on-failure-and-explicit-resume)); P5.2 implements `sequence run` (inputs, context, failure and preview; [evidence](evidence/p5-2-ordered-execution.md)); P5.3 implements records, locking, `show` and `resume` ([evidence](evidence/p5-3-durable-resume.md)). P6.1 fixes the Ralph commands, completion signal, bounds, state and resume ([D045](../DECISIONS.md#2026-11-05--d045-ralph-claim-plus-trusted-check-completion-fresh-iterations-and-explicit-bounds)); P6.2 implements `ralph run`/`show`, fresh iterations, both bounds, records and the shared lock ([evidence](evidence/p6-2-ralph-iterations.md)); P6.3 adds completion verification and `resume`. Workflow coordinators call the same Rust application execution service described in [DESIGN.md](DESIGN.md); they cannot call providers directly or bypass capability/policy validation. They enter after core MVP; durable workflow state is not needed for the first usable single run.

## Sequence inputs and context

General requirements: resolve the ordered input list before launching and keep content identities, so changed prompts cannot silently resume as the same step. Sharing context must not imply cross-provider session portability. Revalidate route/agent restrictions at each step and attempt. Prompt metadata cannot override an explicit invocation-level route restriction.

Selected for Phase 5 (D044):

```bash
ah sequence run prompts/ --mode local-only --permissions trusted --verify test
ah sequence run prompts/ --preview
ah sequence show                       # runs for this project
ah sequence show s20261103T140000Z-1a2b3c4d
ah sequence resume s20261103T140000Z-1a2b3c4d --retry --permissions trusted --verify test
```

- **Options:** the `single` coding options plus `--preview` for `run`. Prompt sources reject; `resume` takes project, config and folder from the record. `--output jsonl` rejects for sequence commands in Phase 5.
- **Snapshot:** DIR is read once, non-recursively, before any key lookup, runtime, network, lock or state write. Names starting with `.` are ignored. Every other entry must be a regular file named `N-slug.md` (`N` 1–6 digits; slug `[A-Za-z0-9][A-Za-z0-9._-]*`; at most 128 bytes); anything else, including symlinks and directories, exits 2. Order is the numeric value of `N`; equal values exit 2. 1–256 steps, at most 16 MiB in all; an empty folder exits 2. Each file follows the single-run prompt rules. Steps run from the in-memory snapshot, so an agent's edits to later prompt files do not change the running sequence. Step identity is the file name plus the SHA-256 of its bytes.
- **Metadata:** optional frontmatter opened by a first line of exactly `---`, at most 16 KiB, strict YAML as for agents. Only `agent` and `verify` exist; unknown or duplicate keys exit 2.
  - `agent: NAME` selects `agents/NAME.md` for the step. With `--agent`, a different name exits 2.
  - `verify: NAME` substitutes another declared check for the step. It requires `--verify`, which in a sequence gates every step and names the default check. Metadata cannot disable the gate.
  - Mode, model, permissions, timeout, sync and commands cannot be set by metadata. Every step's metadata, agent and check is resolved and pinned before step 1 launches.
- **Context:** every step is a fresh single run with its own private runtime, session, grants and preflight, through the same route policy, managed sync and local-first fallback. Only the project filesystem and the step's own prompt carry over. `--timeout-secs` bounds each step attempt; there is no whole-sequence deadline. Each step's human response is written to stdout and flushed when that step's turn ends, before its check or the next step, and ends on its own line (a newline is added if missing; single-run stdout is unchanged). P5.4 found that unterminated responses joined and stayed buffered until exit.
- **Failure:** strictly linear. A step completes only on agent success and, if gated, a `passed` check. Anything else stops the sequence and leaves later steps `pending`; there is no continue-on-failure option. A signal between steps stops before the next launch (exit 3). The sequence exit is the stopping step's exit, or 0 when all steps complete.

## Durable records and resume

General requirements: record workflow, project, ordered-step, input/config/agent, attempt, route/model and verification identities and terminal status. Retain only what recovery needs. Distinguish pending, active, succeeded, failed, cancelled and uncertain attempts. A crash while active does not mean failure without effects. Resume preserves prior results; retry creates a new attempt with a recorded reason. Inspection works without a model. Never delete or rewrite failure evidence. No exactly-once side-effect guarantee or automatic project rollback is promised.

Selected for Phase 5 (D044):

- **Location:** `$XDG_STATE_HOME/agent-harness/` if that is absolute, else `$HOME/.local/state/agent-harness/` (only this fallback needs an absolute `HOME`). The root must lie outside the project. Records are `sequences/RUN_ID.json`; locks are `locks/PROJECT_KEY.lock` (SHA-256 of the canonical project path). Directories are 0700, files 0600, and symlinked components exit 2. `RUN_ID` is `sYYYYMMDDTHHMMSSZ-` plus 8 random hex characters and is checked before any path is formed.
- **Content (`v: 1`):** run identity, timestamps, canonical project/folder/config paths, run status, and ordered steps with name, hash, effective agent and check, and status. Each step attempt keeps its number, reason (`initial`, `resume`, `retry`, `accept`), timestamps, input and agent-definition hashes, check identity (name, pinned program, argv hash), route, model, fallback target, permissions, timeout, agent outcome, exit, D043 verification fields and the D039 per-backend summary. No prompt text, response, check output, argv text, environment names or keys are stored. Limits are 32 attempts per step and 4 MiB per record.
- **Atomicity:** each write is temp-file, fsync, rename, directory fsync (as D025). The record is written before step 1, an attempt is marked `active` before its runtime launches, and its result is written before the next step. A failed write before a launch exits 1 with nothing launched; after an attempt it exits 4. An `active` attempt whose lock is free is `interrupted` and treated as uncertain. The submission boundary is not persisted.
- **Concurrency:** `run` and `resume` hold a nonblocking project lock for their whole duration; contention exits 2 before launch. Single runs do not take it, so a concurrent single run in the same project is unsupported. `show` takes no lock.
- **Resume:** `run` never resumes implicitly; it starts at step 1 and lists unfinished runs for the project. `resume` re-reads the folder. The completed (`succeeded` or `accepted`) steps must still lead, with the same names and hashes in order, or it exits 2. Later steps are re-snapshotted, so a failed prompt can be edited and steps added or removed after the resume point. Route options resolve afresh. Each attempt records its own identities, and human output reports what changed from the step's previous attempt. The first incomplete step decides the next action:
  - Its last attempt never submitted a prompt (`prompt_submitted` false on every backend attempt, including a local-first fallback): resume retries it. Such a step (or an unattempted step) cannot be accepted with `--accept` (exit 2); `--accept` requires an attempt that may have had effects.
  - Otherwise (submitted, uncertain, interrupted or a gate that did not pass): resume exits 2 unless the caller passes exactly one of `--retry` (new agent attempt) or `--accept` (no agent turn; a gated step reruns its check and completes as `accepted` only if it passes; an ungated step is recorded `accepted` and never labeled verified).
  - Gate retention: a step whose last attempt was gated stays gated from the record on any resume (bare, `--retry` or `--accept`), requires `--verify` and the exact same check name (else exit 2), and re-pins that check from current config, reporting a changed identity. This gate requirement is checked before resolving subsequent steps, so later-step metadata errors cannot obscure it. An `accept` attempt is always appended; if its check does not pass, the step takes that result, the run stays stopped and the exit follows D043.
  - No remaining steps: exit 0 without launching. A step with recorded attempts must remain next even then: truncating the folder to the completed prefix exits 2 (P5.3 review).
- **Compatibility and retention:** unknown fields, unparsable files or a `v` other than 1 exit 2 without rewriting. A schema change bumps `v` and decides its migration then. Records are kept until the user deletes them, which is safe while no sequence holds the project lock; there is no pruning command.

P5.3 implementation details within D044:

- **Schema v1 fields:** `v`, `run`, `created`, `updated` (UTC RFC 3339, seconds), `project`, `folder`, `config` (canonical UTF-8 paths; others exit 2 before any write), `status` (`active`, `stopped`, `completed`) and `steps`. A step has `name`, `sha256`, effective `agent` and `check`, `status` and `attempts`. Step and attempt statuses are `pending` (steps only), `active`, `succeeded`, `accepted`, `failed`, `rejected`, `cancelled`, `uncertain` and `interrupted`. An attempt has `number`, `reason`, `status`, `started`, `ended`, `input_sha256`, `agent_sha256` (the definition file's bytes), `check` (`name`, pinned `program`, `argv_sha256` of the JSON array of arguments after the program), `route`, `model` (runtime model), `fallback` (runtime model), `permissions`, `timeout_secs`, `agent_outcome`, `exit`, `verification` (the D043 fields) and `backends` (`attempt`, `launched`, `prompt_submitted`, `backend_stop`, `cleanup_confirmed`, `grants`, `tool_events`). An `accept` attempt has `agent_outcome` null, no backends, and its verification's `agent_outcome` null; its route fields record the resolution at accept time.
- **Owned directories:** the symlink and type rules apply to `agent-harness/`, `sequences/` and `locks/`; ancestors such as `XDG_STATE_HOME` may be symlinks (macOS `/var`). A reused owned directory or lock file must also belong to the current user with no group or other access; otherwise `run`, `resume` and `show` exit 2 before any launch and leave it as found. `Store::existing` (used by read-only `show`) inspects and validates the root and `sequences/`; `locks/` and lock files are checked and validated when writer locks are taken or probed. Creation modes cannot protect objects that already exist, and a permissive store is never repaired, because it may already hold replaced records or locks. The outside-project check resolves the deepest existing ancestor, so a symlinked path into the project is refused before anything is created.
- **Lock holder:** after taking the lock, `run`/`resume` write their run ID into the lock file. `show` reports a run `active` only when the lock file names it and a nonblocking shared probe finds the lock held; the probe is released at once, so a `run` starting in that instant may see contention (exit 2, nothing launched). Otherwise a stored `active` run or attempt is shown `interrupted`.
- **Resume order:** read the record, re-read the folder, plan on a copy with stale `active` attempts marked `interrupted`, then resolve only the remaining steps (completed steps do not need the original options), take the lock, and refuse (exit 2) if the record changed since it was read. The `interrupted` marking is written with the resume; attempt evidence is otherwise unchanged. Only the stopping step can carry attempts; if it was renamed, moved or removed (including a folder truncated to the completed prefix) it exits 2, and any other recorded attempts after the first incomplete step make the record inconsistent (exit 2). `resume` of a run with nothing remaining exits 0 before resolution.
- **Limits:** the 32-attempt bound is checked before resume launches anything. The 4 MiB bound is checked on every write, which then fails as a write failure (exit 1 before a launch, 4 after); a resume is not refused in advance for size.
- **`show`:** `show [--project PATH]` lists the project's runs (default: current directory), one line each, plus unreadable record files with their reason. `show RUN_ID` prints the run, every step and attempt (no prompt text, argv or output) and the next action. An attempt whose result was never written (`active` or stored `interrupted`) shows `prompt submitted unknown`; P5.4 found a stored `interrupted` attempt shown as `no`. Both are read-only and create nothing.

## Verification gates

P5.5 fixes the gate ([D043](../DECISIONS.md#2026-11-03--d043-trusted-verification-gates-for-single-runs-scheduled-before-sequence-decisions)); [EXECUTION](EXECUTION.md#p55-verification-gates-d043) owns its outcomes and exits.

- **Trust:** only harness-config `checks` define commands (argv, no shell). The invocation authorizes one by name with `--verify NAME`. Prompts, agent definitions, model output and prompt metadata cannot define a command. Sequence metadata may reference a declared name only under an invocation `--verify` (D044). A program found inside the project, or reached through an in-project symlink, is untrusted and rejects before launch.
- **Identity and execution:** the program is pinned before launch and run in the canonical project directory, in its own process group, with closed stdin, scrubbed route keys and its own timeout. Records keep the check name, status, exit code/signal, timeout, duration and cleanup. Output is not captured or persisted; sequence records keep the status fields only (D044).
- **Outcomes:** agent outcome and verification status are recorded separately. A check runs only after backend success; without a check, a task is never labeled verified.
- **Stop/repair:** the harness never repairs, retries or re-prompts after a failed gate, and never executes model-suggested commands. In sequences, a step whose gate is not `passed` stops dependent steps; Phase 5 offers no continue-on-failure option (D044). Bounded repair iterations belong to Ralph (D045).

## Ralph loop

General requirements: start each iteration with fresh agent context while reusing filesystem progress and explicit task state. A model assertion, DONE file, or clean exit alone cannot bypass a configured verification gate. Enforce iteration and wall-time bounds, cancellation and a terminal non-completion outcome. Report usage when supplied; do not claim a hard cost bound without timely trusted usage and a defined enforcement mechanism. Reset/retry behavior and backoff must not become an unbounded loop.

Selected for Phase 6 (D045; [study](evidence/p6-1-ralph-study.md)):

```bash
ah ralph run TASK.md --mode local-only --permissions trusted --verify test --max-iterations 10 --max-runtime-secs 3600
ah ralph run TASK.md --verify test --preview
ah ralph show                          # Ralph runs for this project
ah ralph resume r20261105T140000Z-1a2b3c4d --verify test --max-iterations 15
```

- **Options:** the `single` coding options plus `--max-iterations` (1–100, default 10) and `--max-runtime-secs` (1–86400, default 3600); `--preview` for `run`. `--verify` is required. FILE is the only prompt source (no inline, `--prompt-file` or stdin), follows the single-run prompt rules and has no frontmatter. `--output jsonl` rejects. `resume` takes project, config and prompt path from the record.
- **Iterations:** each one is a fresh single run (private runtime, session, grants, preflight; same route policy, managed sync and local-first fallback). FILE is snapshotted once per invocation. The prompt sent is a fixed harness header followed by FILE. The header gives the iteration number and bound, the previous iteration's agent outcome, claim and check status, the check name and the completion instruction. It never carries response text, check output, file content or paths. Task progress lives in project files that the prompt names; the harness does not interpret them. `--timeout-secs` bounds each iteration, capped by the remaining wall time.
- **Completion:** a claim plus a passing check from the same iteration. The claim is the last non-empty line of a backend-success response delivered after `end_turn` and cleanup, exactly `AH-RALPH-COMPLETE` (trailing ASCII whitespace ignored). The check runs under D043 only after a claim. A claim whose check ends `failed` or `timed_out` is rejected and the loop continues; the next iteration is the bounded repair. The marker elsewhere in the text, responses from non-success iterations, earlier iterations' claims, DONE files and clean exits never count.
- **Stopping:** any agent outcome other than success, or a check ending `error`, `cancelled` or with unconfirmed cleanup, stops the run (`stopped`) with its D024/D043 exit. There is no automatic replay, backoff or failure budget. A signal between iterations exits 3 before the next launch. Reaching either bound at an iteration boundary without completion ends the run `exhausted`, exit 1. A wall deadline reached during a turn is that attempt's deadline outcome (3 or 4). A started check keeps its own timeout, so wall time can be exceeded by at most one check timeout plus cleanup allowances.
- **Usage:** no cost or token bound. Per-backend D039 usage objects are recorded; `show` sums reported cost only when every submitted attempt reported one in a single currency, otherwise unknown.
- **Records:** the D044 store, atomicity and per-project lock (shared with sequences). Records are `ralph/RUN_ID.json` (`RUN_ID` starts with `r`), schema `v: 1`, at most 100 iterations and 4 MiB. Run status is `active`, `stopped`, `completed` or `exhausted`. A record also holds the run identity, timestamps, canonical project, prompt and config paths, the run's current iteration bound (`max_iterations`) and each invocation's start, reason (`run`, `resume`, `retry`, `accept`) and wall bound (`max_runtime_secs`). Each iteration keeps the D044 attempt fields plus prompt and sent-input SHA-256, `claim` and per-backend usage; reasons are `initial`, `continue`, `resume`, `retry` and `accept`. No prompt, header, response or check output is stored. An `active` iteration with a free lock is `interrupted` (uncertain).
- **Resume:** never implicit. FILE is re-read; a changed prompt or re-pinned check identity is recorded and reported. The check name must match the record. A `completed` run exits 0. After a last iteration that never submitted, or that ended in backend success without a check stopping the run, bare resume launches the next iteration; a run whose counted agent iterations reached its bound first needs `--max-iterations` greater than that count, while a run exhausted only by wall time resumes under its recorded bound. Otherwise `--retry` (new iteration) or `--accept` is required. `--accept` requires a last iteration that may have had effects, runs no agent turn and does not count toward the bound; if the check passes, the run becomes `completed` with that iteration `accepted`.

## Deferred candidates

Parameterized recipes/templates, native session continuation/fork, user-defined lifecycle hooks, and richer history/export are candidates listed in [FEATURE_REVIEW.md](FEATURE_REVIEW.md). A general DAG scheduler, autonomous parallel teams and automatic Git worktrees remain outside the current roadmap. Reusable prompt folders and named agents are sufficient before usage proves a larger abstraction necessary.
